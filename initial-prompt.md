/grill-with-docs Let's have a deep discussion about how we could design a system that uses Bitcoin Proof of Work mining for passing certain checks and requirements on websites and services, for example, an api or set of apis for a new "turnstile" or "captcha" style check on websites that requires the user to mine some amount with their miner before taking certain actions, like creating an account, or to acquire "credits" on the website in some sort of credit based system to allow them to take actions. Also, we should try to make this api or interface extensible and open source so that anyone can implement a similar api on their own websites, and/or delegate to some sort of host server which essentially coordinates and verifies the client's proof of work and tells the webmaster's backend server that the check was passed. And I am imagining that we need the simplest and fastest onboarding possible for the first time the user runs into this for the first time. My imagined first-time user flow is like so:
- the user gets to a website that requires proof of work mining and is blocked by a kind of capture screen until they pass it, and the screen asks if they have a bitaxe
- if they don't, tell the user a bitaxe is required at a minimum in order to access the website or service and guide them for where and how to get one.
- if they do, tell the user to plug in their bitaxe via usb. If they don't yet have our custom firmware at https://github.com/bright-builds-llc/bitaxe-esp-miner (which we own and can fully customize), then we will prompt the user and guide them on installing it. And technically we will likely need to extend our Rust based fork of the Bitaxe firmware for mining to accomplish this; we can discuss this more.
- once they have the bitaxe plugged in, tell the user that if they don't yet have the custom firmware, then they should back up their mining pool and configuration, because all that info on their bitaxe will be overwritten; perhaps we can create some sort of safer migratory upgrade path which retains the users' current settings in the future.
- once they agree to flashing their bitaxe with the custom firmware, we will onboard the user through the flashing on the web, which should be as simple as possible, and modeled after the official bitaxe web flashing tool (https://github.com/bitaxeorg/bitaxe-web-flasher), for ease of use.
- once their bitaxe is flashed with our custom firmware, we need to ask the user to install an app on their iPhone or Android (we have not yet developed this app but we can discuss the requirements for it for a minimum viable product)
- once they have the corresponding app installed, tell them to scan a QR code on the website, which will act as the pairing process which pairs the plugged in flashed bitaxe with the user's newly installed app on their phone, so that they can interact with and manage and configure their bitaxe from their phone (we can discuss the finer points of this to figure out how it should work); we will want to have a backend so that the user can communicate with their bitaxe (or multiple bitaxes) from anywhere in the world while they are out and about, so that they can, for example, use their bitaxe for mining on any websites in the future that require passing this bitcoin proof of work based turnstile. So we will need to design a simple, nice bitaxe management backend and front ends for the users. Once they have signed up, we also want a full parity web based bitaxe management UI as well as mobile apps.
- once they have paired their bitaxe with their phone and account, we proceed to the turnstiles' next steps of requesting that the user mine some amount of accepted shares in order to pass the turnstile; this required number will likely change over time and will likely need to be administrator/webmaster configurable and perhaps tied to the current mining difficulty or based off it or some linear equation off of it somehow.
- once the user starts mining, we should have the UI of the turnstile indicate this and display turnstile progress. And once they complete it, show a nice completion ui.
- once mining for the turnstile completes, we likely want to allow the user's bitaxe to constantly be mining so that their hardware is not idle. We should prompt the user to add their bitcoin address for mining rewards and indicate to the user how our reward structure is laid out, if they agree to mine on our mining pool. Starting out, since we are starting a new mining pool, we probably can't reward anything at the start until we've bootstrapped our mining pool with enough hash rate. 
- Another cool thing that helps our system come "full circle" is that the user must periodically "donate" shares or "pay" shares of their mining to our pool or a certain amount per period like per day or per month or something, and/or perhaps per api usage, which pays for the cost of maintaining our mining pool backend and bitaxe backend; and we should be totally up front about this to the user and explain our cost structure for how they "pay" to use our service using their proof of work miner. One random example could be like, 1000 accepted shares per day plus 100 shares per 20 api requests or something. And possible, different api requests will have different costs, and we will want to make this configurable by the administrator/webmaster.
- we want our bitaxe management stack to probably be Rust based in the backend and SolidJS based on the front end. It will likely be decoupled from our mining pool backend, but if so, it should interoperate with it seamlessly, and we will likely make this some sort of generic protocol so that others can work off it is and interoperate with it. Perhaps we could define the protocol using protobuffer services and such.

Another question is which open source mining pool software do we want to use in our backend? We should do some research here. I have a strong preference for Rust based mining pools and well maintained pool software. If there is none available, I am ok with porting a modern popular open source mining pool backend from another language into Rust. And it would be nice if we can keep our "additions" to the mining pool backend be as simple and or thin as possible so that it would not be so hard for other mining pool vendors to adopt their own kind of turnstile type system extensions. Perhaps we won't even modify anything at the base layer of the stratum v1 or v2 protocol, and our thing may just be a smart layer on top of those; we can discuss this and tradeoffs and recommendations here. Or we might want a totally distinct and simpler protocol for the turnstile based system if that makes more sense.

We will likely not make the plan for implementing all of this in this repository; we might decide that a lot of this belongs in other repositories or perhaps a monorepo or a few monorepos centered around specific concerns or themes. Let's discuss a sensible setup for our repositories for all of these pieces. All of this will be MIT open source and I want folks to adopt and fork and deploy their own versions of these because I want maximum competition in this space so that we have the best long term outcome and experience for users and the Bitcoin ecosystem.

And we likely want to allow the user to log in using a few different methods, namely, using an email or using nostr nip-46 signing so that they can use another nostr client to log in to our service. And we will never store passwords; we only want passkey style login or email code login or nostr based login.
