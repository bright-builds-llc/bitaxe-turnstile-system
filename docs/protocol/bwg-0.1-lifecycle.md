# BWG/0.1 Lifecycle Control

The Gate Authority persists separate Work Challenge and Work Session state machines. `GET /v0/challenges/{challenge_id}/lifecycle` returns a redacted challenge snapshot containing state, Verified Progress, Work Requirement, the absolute challenge expiry, and whether the retained progress can still lead to authorization. It does not expose claimant keys, Work Session identifiers, lease continuity identifiers, or Worker details.

The Relying Service backend forwards claimant Pause and Cancel intent through its existing service credential. `POST /v0/challenges/{challenge_id}/pause` accepts `user_requested`, `tab_closed`, or `connectivity_lost`; each reason ends active leases while leaving an active challenge and its Verified Progress resumable. `POST /v0/challenges/{challenge_id}/cancel` requires `{"confirm_progress_loss":true}` and terminally makes retained progress ineligible. A challenge identifier alone never authorizes these commands.

The claimant can also act on its own authority (ADR-0106). `POST /v0/challenges/{challenge_id}/work-session/{start,resume,renew,pause,cancel,pool-selection}` each needs a `bwg-claimant-proof` header carrying a single-use `bwg-work-session-proof+jwt` from the challenge's claimant key. Its claims bind `htm` `POST`, the exact public `htu`, `challenge_id`, an `iat` within 60 seconds, and `request_sha256`, the base64url SHA-256 of the exact body. Start takes `control_session_binding_sha256` and, when the challenge requires it, `trusted_consent_receipt`; Resume takes the fresh digest; Renew takes the active digest and `lease_id`. Pause and Cancel take the same bodies as the Relying Service routes. Start and Resume return a Controller 0.4 `WorkerLeaseGrant`, and Renew returns a `WorkerLeaseRenewal`, each carrying an ADR-0093 authorization the device verifies. Resume confirms the paused session's restoration before it starts a new lease. The lease clock is the Authority's own millisecond clock under the digest as continuity, so Renew under another digest ends the lease. `POST /v0/challenges/{challenge_id}/work-session/pool-selection` (ADR-0107) takes `pool_offer_id`, `payout_destination_type` and `payout_destination` under the same proof, and consents to that choice. It answers the offer ID and `payout_commitment` only. The raw choice goes to the Pool Adapter; the Authority never stores or logs it. A replay succeeds, and a different choice after consent answers 409 `pool_selection_locked`. Without a deployed Work Lease Authority key these routes answer 503 `worker_lease_unavailable`; the `gate-authority` binary enables them from `BWG_WORK_LEASE_AUTHORITY_SEED`, `_KID` and `_ISSUER`, `BWG_STRATUM_CREDENTIAL_KEY`, `BWG_WORKER_STRATUM_ENDPOINT` and `BWG_POOL_ADAPTER_DATABASE_URL`.

The Pool Adapter prepares a session in `ready`, starts or renews one bounded monotonic Work Lease in `leased`, moves an ended lease to `stopping`, and records Worker confirmation as `restored`. A failed session remains `failed`. A session cannot be leased again until restoration is confirmed, and no session can resume a cancelled or expired challenge.

One Work Lease lasts at most 60 seconds and should be renewed every 20 seconds. A renewal retains the lease identity only when its boot-continuity identifier is unchanged, its monotonic reading has not decreased, and the prior monotonic deadline has not arrived. Reboot, monotonic reset, uncertain time, and lease expiry clear the lease and request Mining Baseline restoration. An Accepted Work Event is judged by the reading at which the Pool Adapter observed it, not by when or in what order it arrives. It must name the active lease and continuity, read no earlier than the lease's start, and fall before the lease's current expiry; event and share deduplication stop a second credit. So work observed before a Renew still counts when it is delivered after it. Work delivered after Pause, Cancel, satisfaction or the challenge deadline is refused and never credited. The deadline is judged by the Authority's clock at delivery as well as the receipt time (ADR-0108).

The lifecycle snapshot also publishes `lifecycle_deadline_unix_seconds`, which is the Work Challenge deadline before issuance and the Gate Pass deadline after issuance. Connected SSE clients receive an `expired` lifecycle event when that deadline arrives.

The BWG/0.1 reference profile uses a 15-minute Work Challenge, a two-minute Gate Pass, a 60-second single-use DPoP freshness window, and zero verifier clock-skew extension. Future-issued DPoP proofs are invalid. The signed or persisted deadline is the first invalid instant.
